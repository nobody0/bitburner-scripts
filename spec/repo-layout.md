# Repository layout

Five parts, one rule each:

| Directory | Rule |
|---|---|
| `game/`   | The ONLY code that reaches the game. Entrypoints listed in `bitburner.config.json` (validation rejects sources outside `game/`), bundled standalone by esbuild, pushed over the Remote File API. `start.ts` is the tiny autoexec/sync wrapper; `main.ts` boots the loop in `lib/controller.ts`. The game-state store is `lib/state.ts`, acquisition is `lib/probe-runner.ts` + `lib/probes/`, the write half is `lib/features/`, and `lib/telemetry*.ts` is the optional send. Plus `lib/ns-proxy.ts` + `lib/ns-resident.ts` and the puppet worker. |
| `shared/` | Self-contained pure code used by two or more parts: telemetry schema, the WorldView/Action/Planner seam, goals + the stream reducer, strategy. `game/` may import it and the bundler folds it into standalone game artifacts. It may use erased `import type` declarations from `@ns`, but has no runtime Netscript dependency, no imports from another project directory, no host APIs, and no `__TELEMETRY__`. |
| `sim/`    | The test loop. Runs the REAL `game/` controller against a synthetic world: `realm/` (virtual time + the unmodelled-gap reporter), `ns/` (synthetic Netscript, process table, transcribed RAM costs), `game-run.ts` (wires them together), `engine.ts` (the 200 ms game cycle). Plus `vendor/bitburner/` (generated by `bun run vendor` from the pinned tag — DO NOT EDIT), `core/` (transcribed effects, mocks, rng), `clock.ts`, `world.ts`, `run.ts`, `profiles.ts`, `compare.ts`, and simulator-specific tests under `tests/`. Runs under Bun only. `sim/` may import `game/`; never the reverse. |
| `ui/`     | The external UI process: telemetry hub (`server.ts`, port 12526) + browser viewer. The viewer is TypeScript under `app/` (shell + `project.ts` + one module per feature tab), bundled on demand by `Bun.build` inside the hub and served as `/app.js`; `public/index.html` is the static shell; `public/theme.css` carries the Bitburner theme tokens and shared primitives (the copy-source for any sibling page), `public/app.css` the viewer-specific chrome. No separate build step — the hub rebuilds when a source file changes, so a refresh is the whole dev loop. Tabs are pure string builders and the panel is PATCHED into the live DOM (`app/lib/morph.ts`), never reassigned to `innerHTML`: a live run re-renders twice a second, and replacing the subtree would destroy the reader's selection, caret, hover, open disclosures and scroll offsets on every frame. Interaction state that markup must re-assert (filters, sort, search text, which disclosures are open) lives in `app/lib/viewstate.ts`, written by the delegated listeners in `main.ts`. Runs under Bun only. |
| `saves/`  | Exported Bitburner saves plus `index.json`, the registry naming them. A snapshot is what a simulation run starts from; runs seeded from the same snapshot are comparable with each other and with nothing else. Blobs are committed. See `spec/saves.md`. |

Plus: `tools/` (build/sync/vendor tooling, save IO and restore), `spec/` (these
documents), `tests/` (cross-project and tooling tests), `types/` (game-provided
NetscriptDefinitions), `runs/` (gitignored JSONL telemetry, one file per run;
`runs/pinned/` survives the retention sweep).

## Daily commands

```
bun run ui           # telemetry hub + viewer, with a manual sync button
bun run sync         # one-shot build + push (+ stale-file sweep) without the UI
bun run sim -- --list                       # named profiles
bun run sim -- --profile hacking-early --goal earn:5e6 --seeds 1..3
bun run sim -- --goal earn:1e6 --seed 1     # simulate; JSONL lands in runs/
bun run sim -- --profile factions --save bn5-start
bun run sim:compare runs/a.jsonl runs/b.jsonl
bun run saves                               # registered save snapshots
bun run save:add <id> <file> [label]
bun run save:restore <id>                   # push a snapshot into the game
bun run vendor       # re-extract game formula core from the pinned tag
bun run typecheck && bun run typecheck:vendor && bun test
```

## Current intent (keep it simple)

The controller drives the HWGW engine (`shared/strategy/`) live, through
`game/lib/features/hacking.ts`. All fourteen features are implemented behind the
seam (`shared/world.ts`), each with a probe, a topic, a tab and — for some — a
sim model. See `spec/features.md` for the roster and `spec/progress.md` for what
each one is proven by.

Acquisition is never conditional. Every getter and probe runs in every
build and writes to `game/lib/state.ts`; `--perf` removes the telemetry send
and nothing else. See `spec/telemetry.md`.
