# The darknet

The ground truth of the darknet mechanic, and the remote-execution model our
code builds on it. The mechanic is not a BN15 curiosity: access is BN15, an
active SF15, **or** `DarkscapeNavigator.exe` on home
(`shared/features/unlock.ts`), and the labyrinth pays out in thirteen of
fifteen BitNodes. Node-specific rules — multipliers, SF15's levels, where the
Red Pill sits — are in [`spec/strategy/bitnodes/bn15.md`](strategy/bitnodes/bn15.md);
the feature machinery is in [`spec/features.md`](features.md).

Every game fact below is verified against the pinned checkout at
`../bitburner-src` (`spec/game-source.md`) and cited `file:line`, same contract
as `spec/strategy/README.md`. Unprovable things are questions in **Open**.

## The four constraints

Everything else in this document is downstream of one of these.

**There is no global view.** `ns.dnet.probe()` returns only the darknet servers
directly connected to *the calling script's own host*. From `home` that is
`darkweb` and nothing else, and `ns.scan` does not enumerate the darknet at all.
A map of the darknet can only be assembled from reports by scripts standing in
different places.

**Sessions belong to a PID.** `authenticate(host, password)` grants a session to
the calling script instance only; the docs are explicit that "other running
scripts will need to use `connectToSession` with the correct password to also get
a session". No channel — file, port or page realm — can transfer one. This is
why a dodge stub cannot win a session on the controller's behalf: the stub dies,
and the session dies with it.

**Transfer is distance-free; execution is not.**

| Operation | Requires |
|---|---|
| `scp` *from* a darknet host | nothing at all |
| `scp` *to* a darknet host | a session — but **no** direct connection, at any distance |
| `writePort` / `readPort` | nothing; ports are shared across all hosts, 0 GB |
| `ns.exec` on a darknet host | a session **and** a direct connection, backdoor, or stasis link |

So getting *data* around is nearly free, and getting a *running process* to
depth *n* is the hard problem. Everything upstream of that is a credential
problem — **except the first hop, which is free.**

`darkweb` is a deliberate special case, generated by `initDarkwebServer()`
(`DarkNet/controllers/NetworkGenerator.ts:52-89`): `modelId: NoPassword`,
`password: ""`, `depth: -1`, `difficulty: 0`, `preventBlockedRam: true`,
`isStationary = true`, `hasAdminRights = true`, `blockedRam = 0`, `maxRam = 16`.
`isAuthenticated()` short-circuits true for it
(`DarkNet/effects/authentication.ts:199-205`), and so does the `exec`/`scp`
gate — *"We always are authed to ourselves and DarkWeb. Early-out past the last
checks."* (`DarkNet/effects/offlineServerHandling.ts:98-101`). So an agent can
be deployed to `darkweb` and run there with no credential, no session and no
cracking, on a full 16 GB, forever — it never moves. Its depth of `-1` also
confirms that depth 0 is its children, not itself.

**But read the check ORDER, because the early-out is narrower than it looks.**
`checkDarknetServer` evaluates `requireDirectConnection` *before* reaching that
early-out (`offlineServerHandling.ts:82-100`), and `ns.exec` passes
`requireDirectConnection: true` (`NetscriptFunctions.ts:641-646`). The early-out
skips the admin-rights and session checks; it does **not** skip the connection
check. Only `home` holds the TOR edge to `darkweb`, so:

> **`ns.exec` onto `darkweb` works from `home` and from nowhere else.**

`ns.scp` passes no connection requirement at all (`NetscriptFunctions.ts:769-773`),
so *copying* to `darkweb` works from any host — which is why the seeding dodge may
be placed anywhere to `scp`, but must be pinned to `home` to `exec`. A dodge stub
landing on an arbitrary leased fleet host would `scp` successfully and then get a
silent `0` from `exec`, which is indistinguishable from "the host is full".

That is the beachhead the whole feature stands on: from `darkweb`, `probe()`
finally returns the depth-0 servers that `home` cannot see, and cracking starts
from there.

**The map moves.** `nextMutation()` resolves when servers move, restart (killing
their scripts), go offline — often permanently — or appear fresh with new
passwords. The clock is quantified under [The mutation clock](#the-mutation-clock).

## The `ns.dnet` surface

| Call | Role |
|---|---|
| `probe()`, `getServerDetails`, `getDepth`, `isDarknetServer`, `getServerRequiredCharismaLevel` | Enumerate and select targets, all **local to the calling host** |
| `authenticate(host, password)` / `connectToSession(host, password)` | Access — the first needs a direct connection, the second does not. Both grant a session to the calling PID only |
| `heartbleed(host, options)` | Scrape logs. Needs a direct connection and **charisma ≥ the host's requirement**, but no session. Threaded, priced by `formulas.dnet.getHeartbleedTime` |
| `openCache(filename)` | Retrieve captured data. Returns `karmaLoss` — it is a karma sink, which couples it to `career` and `gang` |
| `memoryReallocation()`, `getBlockedRam()` | Free RAM held by the server owner's processes. Needs an authenticated, directly-connected target; scales with charisma and threads |
| `setStasisLink()`, `getStasisLinkLimit()`, `getStasisLinkedServers()` | **Takes no host** — pins the *calling script's own server* against moving or going offline. So pinning anything requires already running there. The global limit makes links scarce |
| `induceServerMigration(host)` | *Raises the chance* a connected, non-stationary host moves. Scales with threads and charisma. Cannot target its own host |
| `getDarknetInstability()` | Backdoor-induced **authentication** unreliability: `authenticationDurationMultiplier` and `authenticationTimeoutChance`. Unrelated to the map clock |
| `nextMutation()` | The map's own clock (0 GB) |
| `unleashStormSeed()` | Runs `STORM_SEED.exe` if present on the calling host. Documented as catastrophic |
| `promoteStock(sym)` | Raises a symbol's **volatility**, not its forecast. Earns nothing directly — it is a `stock` input (see [Stock propaganda](#stock-propaganda)) |
| `phishingAttack()` | **Only from scripts on darknet servers.** Builds charisma, lifts money scaling with threads, occasionally yields a `.cache` file |
| `labreport()`, `labradar()` | Labyrinth. 0 GB, `Result<any>`, and documented only as riddles — whether they are getters or actions is **unknown** |

There is no scriptable "buy DarkScape" in `ns.dnet`: the purchase is
`singularity.purchaseTor()` then
`singularity.purchaseProgram("DarkscapeNavigator.exe")` — $200k + $50m. The $30m
"Shadowed Walkway" discount is a UI button with no Singularity entry point
(`shared/strategy/dnet/rates.ts:101-115`).

## Network shape

From `DarkNet/Enums.ts:4-11`:

| Constant | Value |
|---|---|
| `NET_WIDTH` | 8 |
| `MAX_NET_DEPTH` | 40 |
| `AIR_GAP_DEPTH` | 8 — depths 8, 16, 24, 32 are structurally empty, so the net is genuinely segmented |
| `SERVER_DENSITY` | 0.6 |
| `LOW_LEVEL_SERVER_DENSITY` | 0.7 |
| `HORIZONTAL_CONNECTION_CHANCE` | 0.5 |
| `VERTICAL_CONNECTION_CHANCE` | 0.3 |
| `MS_PER_MUTATION_PER_ROW` | 30 000 |

The net is a grid: `NET_WIDTH = 8` columns by `getNetDepth()` rows, filled to
`SERVER_DENSITY = 0.6` (0.7 for the shallow rows). `populateDarknet` seeds
`getNetDepth() * NET_WIDTH * SERVER_DENSITY - 10` servers, then tops rows 0 and
1 up to five each, then calls `balanceDarknetServers()`.

`getNetDepth()` is the current labyrinth's depth, so the net grows as the
labyrinth is walked (`DarkNet/effects/labyrinth.ts`, `labData`; transcribed as
`LAB_LADDER` in `shared/strategy/dnet/rates.ts`):

| Lab | Net depth | Charisma | Solved by |
|---|---|---|---|
| *(before full darknet access)* | **5** | 300 | — |
| NormalLab | 7 | 300 | **manual** |
| CruelLab | 12 | 600 | **manual** |
| MercilessLab | 19 | 1500 | script |
| UberLab | 23 | 2500 | script |
| EternalLab | 29 | 3000 | script |
| EndlessLab | 31 | 3500 | script |
| FinalLab | 36 | 4000 | script |
| BonusLab | 36 | 4000 | script |

So roughly 14 servers at depth 5, ~24 at depth 7, and ~163 at depth 36. Depth
also sets the mutation rate, so a deeper net is both larger and faster-moving.
`manual: true` on the first two labs means those two mazes are solved in the UI,
not by a script. (`getNetDepth()` reads `getLabyrinthDetails().depth ?? 10`, but
the `?? 10` is dead code: the no-access branch returns a literal `depth: 5` and
every lab rung carries a depth — `labyrinth.ts:393-396, 485-497`.)

## The mutation clock

`getDarknetCyclesPerMutation()` is `(rateMultiplier × 150) / depth` cycles of
200 ms, `rateMultiplier` being 1 in BN15 and **2 everywhere else**. At the
pre-labyrinth depth of 5 that is a tick every **6 seconds** in BN15 and 12
elsewhere, and it accelerates as the labyrinth deepens — every 4.3 s at the
first lab's depth of 7 — partly offset past depth 16 by `mutateDarknet`'s own
`16 / depth` throttle roll.

One tick then rolls independently for island moves (30%), low-level restocking
(30%), deleting 1-4 servers (10%), adding 1-4 (10%), restarting one (20%),
moving three (30%), adding connections (50%), and severing every connection on
one host (50%) — so most ticks change something, and a fair number change
nothing. `moveDarknetServer` deletes a server outright if `getAllOpenPositions`
returns nothing for it, so a full net loses hosts through the move path as well
as the delete path.

The two clocks must not be confused: the *net* churns in seconds, while any
*named host* is stable for minutes, because a tick touches only a few of
`depth × NET_WIDTH × SERVER_DENSITY` servers. Both figures are transcribed in
`shared/strategy/dnet/rates.ts`, and the knowledge expiry below is derived from
them.

## Passwords and the oracle

Every non-labyrinth server has a `password` (max length 50,
`DarkNet/Constants.ts`) and a `modelId` naming its minigame — *"Similar models
have similar vulnerabilities. The model list is intentionally undocumented. You
are supposed to experiment and discover the models."* `getServerDetails` exposes
`passwordLength`, `passwordFormat`
(`numeric | alphabetic | alphanumeric | ASCII | unicode`), `passwordHint`,
`data` ("Data from the passwordHint, if any"), `logTrafficInterval`,
`difficulty` and `isStationary` — but never the password.

The in-game literature is the teaching material: `Literature/Enums.ts` names
eleven darknet `.lit` files whose enum keys say what each covers —
`FactoryDefaultHint`, `DogNameHint`, `PasswordServerHint` (partial-password),
`TimingServerHint`, `BinaryServerHint`, `StasisLinkHint`, `ServerOfflineHint`,
`DarkWebRebootHint`, `CacheHint1/2`, `LabHint`, and `DarknetHandbook`.

**The oracle is `heartbleed`'s log ring, not the return value of `authenticate`.**
This is the opposite of what it looks like, and getting it backwards makes the
whole password mechanic seem unreachable from a script.

`handleAuthentication` builds a model-specific `PasswordResponse`
(`{code, message, data, passwordAttempted}`) on a wrong password — but
`authenticate()` only forwards its `data` for the **labyrinth**:

```ts
// NetscriptFunctions/Darknet.ts:163-177
if (isLabyrinthServer(server.hostname)) {
  return { success, code, message: authResult.response.message, data: authResult.response.data };
}
return { success, code, message: success ? Success : AuthFailure };   // no data, generic message
```

For every other model the response is written to the server's own log ring by
`logPasswordAttempt` (`DarkNet/effects/authentication.ts:174-177` →
`DarkNet/models/packetSniffing.ts:90-125`), and comes back only through
`heartbleed`, which serialises each entry as
`typeof log.message === "string" ? log.message : JSON.stringify(log.message)`
(`NetscriptFunctions/Darknet.ts:286-288`).

So the oracle loop is **`authenticate(wrong)` → `heartbleed(peek)` → parse the
JSON lines**, and both halves must be the same agent standing on the same host —
`heartbleed` needs a direct connection too. That is a hard constraint on where
the cracking code can live, not an implementation detail.

### The logs leak passwords outright

`heartbleed` is not only the oracle channel; it is a **credential channel**, and
this is the "leaky logs" the node description names. `getLogNoise`
(`DarkNet/models/packetSniffing.ts:154-192`) emits one line per
`logTrafficInterval`, drawn from:

| Line shape | What it leaks | Chance |
|---|---|---|
| `Connecting to <host>:<password> ...` | a **neighbour's plaintext password** | `0.05 x 1/(difficulty+1)` |
| `Logging in with passcode: <password> ...` | **this host's own password** (`OpenWebAccessPoint` only) | ~0.3 of its noise draw |
| `--<password>--` | a random *movable* host's password, unattributed | 0.05 |
| `There's definitely a X and a Y...` (8 templates) | two characters contained in this host's password | 0.1 |
| `The characters A, B are in the right place.` | which characters of the **last attempt** were correctly placed | 0.1 |
| `[sending transaction details to <host>.]` | a topology edge | 0.05 |
| `<time>: <host> - heartbeat check (alive)` | liveness | otherwise |

`capturePackets` additionally embeds ` <hostname>:<password> ` inside a ~130-char
junk blob whenever `difficulty <= 16`, and the bare password above that.

The consequence for strategy is large: **a log-mining pass is a credential source
independent of every one of the 24 minigames.** Combined with the difficulty
tiering below, it is why the shallow net can be traversed without solving a
single password puzzle.

`requiredCharismaSkill` is rolled as `max(floor(depthScaling + levelVariance), 1)`
where `depthScaling = depth < 2 ? depth * 10 : (depth / labDepth) ** 1.5 *
labCha * 0.85` and `levelVariance = (random * 3 - 1) * depth`.
`logTrafficInterval` is `1 + 30 * 0.9 ** difficulty` seconds.

### Models are drawn by difficulty tier, and the shallow net is soft

`getRandomServerConfigBuilder` (`DarkNet/controllers/ServerGenerator.ts:18-62`)
does not draw uniformly. The pool is banded, and the bands matter more than any
individual minigame because they decide what the first hop actually meets:

| Tier | Models |
|---|---|
| 0 | `ZeroLogon` |
| 1 | `DeskMemo_3.1`, `FreshInstall_1.0`, `CloudBlare(tm)` |
| 2 | `Laika4`, `NIL`, `Pr0verFl0` |
| 3 | `PHP 5.4`, `DeepGreen`, `BellaCuore`, `AccountsManager_4.2`, `OctantVoxel`, `Factori-Os`, `OpenWebAccessPoint` (+ `KingOfTheHill`, `RateMyPix.Auth` with full darknet access) |
| 4 | `PrimeTime 2`, `TopPass`, `EuroZone Free`, `2G_cellular`, `110100100`, `MathML`, `OrdoXenos`, `BigMo%od` |

| `difficulty` | Pool |
|---|---|
| ≤ 2 | tier 0 + tier 1 |
| ≤ 4 | tier 0 + tier 1 **twice** + tier 2 + tier 3 |
| ≤ 8 | tier 1 + tier 2 + tier 3 |
| ≤ 18 | tier 2 + tier 3 + tier 4 |
| > 18 | tier 3 + tier 4 |

`difficulty` tracks the server's original depth, so **at depth 0-2 the pool is
four models, of which two are dictionary attacks with four-entry dictionaries**:
`ZeroLogon` (dictionary `[""]`) and `FreshInstall_1.0`
(`["admin", "password", "0000", "12345"]`). Two more are exhaustible the same
way wherever they appear: `Laika4` (`["fido", "spot", "rover", "max"]`) and
`EuroZone Free` (the EU country list); `TopPass` draws from
`commonPasswordDictionary`, which is bounded but long. All five go through the
same one-line `getDictionaryAttackConfig`, which is why they are a single
implementation in `shared/strategy/dnet/models.ts` rather than five. Everything
else is a genuine minigame.

## RAM on darknet servers

`maxRam` is rolled at construction (`DarknetServerOptions.ts:206-211`):

```
baseRam = 16 * 2 ** floor(difficulty / 6)
maxRam  = max(baseRam * pick([0.5, 1, 1, 1.15, 1.4]), 16)
```

so 16 GB minimum, doubling every 6 difficulty steps — 128 GB and more in the
deep net. `blockedRam` is then rolled from `maxRam` (`ramblock.ts:97-110`), and
it is a large fraction of the total:

| `maxRam` | `blockedRam` drawn from |
|---|---|
| 16 | `[0, 1, 2]` — index over the first **2** entries only, so 0 or 1 |
| ≤ 32 | `[0, 2, 4]` — likewise 0 or 2 |
| ≤ 64 | `[16, 32, maxRam - 8]` |
| > 64 | `[maxRam, maxRam - 8, maxRam - 64, maxRam / 2]` |

A large server can therefore arrive with **all** of its RAM blocked.
`server.updateRamUsed(server.blockedRam)` is applied at construction, by
`applyRamBlocks()`, and again in `NetscriptWorker.ts:243` whenever a server's
used RAM is recalculated — so blocked RAM presents as *used* RAM and cannot be
allocated. Usable RAM is `maxRam - blockedRam`.

`memoryReallocation` reduces `blockedRam` by
`clamp(0.02 * 2 * 0.92^(difficulty+1) * threads * (1 + charisma/100), 0,
blockedRam)` (`DarkNet/effects/ramblock.ts:71-83`), rounded to two decimals —
freeing meaningful RAM is a many-call grind, scaled hard by charisma and
difficulty. It awards `charisma_exp * threads * 10 * 1.1^difficulty` charisma
xp, and when `blockedRam` reaches 0 on a non-labyrinth server it calls
`addCacheToServer(server, false)` — clearing a server's block yields a `.cache`
file.

What that RAM can and cannot run:

- **`hack`, `grow` and `weaken` cannot target a darknet server.** They resolve
  through `getNormalServer`, which rejects anything that is not a `Server` with
  "The server must not be a darknet server." `DarknetServer extends BaseServer`,
  not `Server`, so it has no `moneyAvailable`, `hackDifficulty` or
  `requiredHackingSkill` at all.
- **Scripts running *on* a darknet server are ordinary scripts.** `cpuCores` is
  fixed at 1; the host works as an execution platform for work aimed at ordinary
  servers.
- Its RAM is not fleet RAM: `ns.scan` omits darknet servers, so they never enter
  the server snapshot or the heap.
- A restart kills every script on the host and clears its sessions; a delete
  takes its files too.

## Backdoors and stasis links

A backdoor is the only unlimited way to `exec` on a darknet host that is not
directly connected: `ns.exec` calls the darknet gate with
`backdoorBypasses: true` (`NetscriptFunctions.ts:641-646`), so
`backdoorInstalled` satisfies the direct-connection requirement. The only other
bypass is a stasis link — and there are at most four of those, ever.

Three costs attach to a backdoor:

1. **Global authentication slowdown** of `1.07 ^ surplus`, where the free
   allowance is `max(rootedMovable / (NET_WIDTH * 3), 2)` — movable servers with
   `hasAdminRights`, over 24 (`DarkNet/effects/effects.ts:92-98`). So at least
   two backdoors are always free, realistically two to four, and the allowance
   grows as you root more of the net. `getDarknetInstability()` reports exactly
   this surplus — instability and mutation are unrelated mechanics, and
   instability never moves a server.
2. A ~9% chance per mutation tick that one backdoored host is restarted. A
   restart kills its scripts, clears `authenticatedPIDs`, and sets
   `backdoorInstalled = false` (`NetworkMovement.ts:301-311`).
3. A ~4% chance per tick that one backdoored host is deleted. Both branches
   `return` early, so they also skip the tick's remaining rolls.

**Stasis links** (`DarkNet/effects/effects.ts:211-216`): the limit is
`1 + TheBrokenWings + TheHammer + TheStaff`, so **1 to 4**, raised only by those
three labyrinth augmentations. Applying one costs 12 GB and
`(1000 / (charisma + 1000)) * 30_000` ms on the target itself —
`setStasisLink()` takes no host. `isImmutable(server) = openServer ||
isConnectedTo || hasStasisLink` (`NetworkMovement.ts:227-228`) is checked by
`deleteDarknetServer`, `moveDarknetServer` and `restartServer`, each returning
early on it — a stasis-linked host is not deleted, moved or restarted.

| | Count | Grants | Costs |
|---|---|---|---|
| Backdoor | unlimited | remote `exec` | auth slowdown past the free allowance; restart/delete targeting; the restart clears the backdoor |
| Stasis link | 1-4 | remote `exec`, and exemption from delete/move/restart | a limited slot; 12 GB and the apply time on the target |

So backdoors are the expendable frontier and stasis links pin what we cannot
afford to lose. The strategic loop the docs never note: labyrinth rewards buy
stasis capacity, stasis capacity holds more of the graph, and holding the graph
is what makes the labyrinth walkable.

## Verified formulas

**Authentication time** (`DarkNet/effects/effects.ts:60-89`):

```
baseTime      = 850
skillFactor   = (5 * requiredCharismaSkill + (difficulty + 1) * 100) / (charisma + 150)
threadsFactor = 1 / (1 + 0.2 * (threads - 1))          // diminishing returns
backdoorFactor    = 1.07 ^ max(0, backdoored - max(rootedMovable / (NET_WIDTH * 3), 2))
underleveledFactor = charisma <= requiredCharismaSkill && depth > 1
                     ? 1.5 + (requiredCharismaSkill + 50) / (charisma + 50) : 1
bootsFactor   = has The B00ts of Perseus ? 0.8 : 1
sf15Factor    = activeSourceFileLvl(15) > 2 ? 0.8 : 1
time = baseTime * skillFactor * backdoorFactor * underleveledFactor
       * bootsFactor * sf15Factor * threadsFactor
return time * intelligenceBonus(intelligence, 0.25)
       + (modelId === "2G_cellular" ? correctChars : 0) * 50 * threadsFactor
```

Two things worth reading twice:

- **The timing oracle runs the counter-intuitive way.** On `2G_cellular` each
  *correct* character makes authentication take **longer** (+50 ms × threads
  factor). Slower is closer, so the attack measures duration and climbs.
  `formulas.dnet.getAuthenticateTime` documents its fourth parameter as "only
  used for `2G_cellular` model servers" — the one upstream admission that the
  oracle exists.
- **`underleveledFactor` only bites below depth 2.** At depth 0 or 1, low
  charisma costs nothing beyond `skillFactor`.

**Heartbleed time** is `calculateAuthenticationTime(...) * 1.5`
(`NetscriptFunctions/Formulas.ts:492-498`).

## Caches

`.cache` files sit on a server in `DarknetServer.caches` and are listed by
`ns.ls`. They are created by clearing a server's blocked RAM, and by
`phishingAttack()` — a phishing cache is named `.d.cache`.

`openCache(filename)` deducts `difficulty + 1` karma (returned as a negative
`karmaLoss`) and yields one reward drawn at random from:

- a program or stock-market-related reward,
- a stock reward,
- a data file (`DarknetConstants.DataFileSuffix` is `.data.txt`),
- a coding contract — **only** for `.d.cache` files, i.e. from phishing,
- money — **only** when the node's `DarknetMoneyMultiplier` is non-zero.

On a labyrinth server, the labyrinth cache instead calls `getLabReward()`.

The program/market branch is the valuable one, and it is an ordered ladder
(`cacheFiles.ts:130-168`): the first program not already owned, walking
`ServerProfiler, BruteSSH, DeepscanV1, FTPCrack, AutoLink, relaySMTP,
DeepscanV2, HTTPWorm, SQLInject, Formulas` — so a cache can hand over
**`Formulas.exe`**, which the dark web sells for $5b. Once all ten are held it
grants, in order, a **WSE account** ($200m) and then **TIX API access** ($5b).

Then it grants `has4SData` — and that is the **$1b ticker, not the $25b script
API**. `shared/strategy/stock/decide.ts` documents that `getForecast` and
`getVolatility` check `has4SDataTixApi`, which caches never grant, so the free
4S is worth an automated player exactly what the purchase we deliberately never
make is worth: nothing. When everything above is held the branch falls through
to money.

The money reward is
`1.2^difficulty × 1e7 × (200 + charisma)/200 × sf15_3 × crime_money ×
dnet_money × DarknetMoneyMultiplier`, where `sf15_3` is 1.5 at SF15.3, and
`DarknetMoneyMultiplier` is node-dependent (see the BN notes) — that is the only
place `dnet_money` is read. Upstream attributes this to a `darknet` money source
(`MoneySourceTracker`), which the ns `MoneySource` interface does **not**
expose — so a script cannot see darknet income as its own line.

## The labyrinth

`DarkNet/effects/labyrinth.ts` awards a fixed augmentation sequence; the
authoritative order is the prereq chain in `AugmentationTable`:

The W1ngs of Icarus → The B00ts of Perseus → The H4mmer of Daedalus →
The St4ff of Asclepius → The L4w of Bayes → The B1ade of Solomonoff

The rewards are an engine, not just a gate toll. Each costs `rep: 10000` and
`$1e6` with no faction, is `special: true`, and carries multipliers: five of the
six raise `charisma` (The St4ff raises `charisma_exp` instead), and five carry
**`dnet_money`** — 1.3 / – / 1.1 / 1.1 / 1.15 / 1.1 in the order above, The
B00ts being the exception. They are not bought: `getLabReward()` calls
`Player.queueAugmentation(reward)` directly, so they cost no money and no
reputation and belong to no faction — but being queued, they still require an
install to take effect. If the next reward is already owned, the cache awards
**NeuroFlux Governor** instead.

Three of them raise the stasis-link limit by 1 each: The W1ngs of Icarus, The
H4mmer of Daedalus and The St4ff of Asclepius. The B00ts of Perseus multiplies
authentication time by 0.8. Where the Red Pill sits in the sequence is
node-dependent — see [`bn15.md`](strategy/bitnodes/bn15.md).

## Stock propaganda

`promoteStock` is the one darknet call whose entire payoff lands in another
feature, and it is small enough to state exactly. Transcribed from
`src/NetscriptFunctions/Darknet.ts:582` and `src/DarkNet/effects/effects.ts:197`
(both hash-pinned by `sim/tests/drift-pins.test.ts`), and modelled in
`sim/features/dnet.ts` + `sim/ns/dnet.ts`:

| | |
|---|---|
| Preconditions | valid symbol (**not** TIX-gated), running **on** a darknet server, darknet access |
| Wait | `max(8000 * (600 / (600 + cha)), 200)` ms — charisma buys it down to a 200 ms floor |
| Charges bought | `threads * ((500 + cha) / 500)`, priced by charisma as it stands when the call lands |
| Charisma XP | `charisma_exp * threads * 10 * ((200 + cha) / 200)` — so calls compound: each one makes the next cheaper and bigger |
| Volatility multiplier | `1 + (1 - e^(-0.001·c)) + 2·(1 - e^(-0.00015·c))`, approaching **4x** |
| Decay | charges `*= 0.4` once per **market cycle** (75 ticks), from inside `stockMarketCycle` — not per tick |
| Reset | cleared by prestige, on the same boundary at which the portfolio is destroyed |

Two consequences for strategy. It is a **maintenance** cost, not a purchase: a
0.4x decay every 75 ticks leaves a promotion at 6.4% of itself after three
cycles and 1% after five. And it is worth nothing on its own — volatility is
symmetric, so it only pays on a symbol whose forecast already favours a side,
where it widens the same edge `breakEvenTicks` is measured against.

**BN8 relevance.** BN8 zeroes `DarknetMoneyMultiplier` and
`DarknetLabyrinthRewardsTheRedPill`, so the darknet earns nothing there — but
nothing zeroes propaganda, and access needs only `DarkscapeNavigator.exe`
through TOR. In the node where the market is the only income, this is the one
darknet call that still pays.

## The rule: expiry

> **No darknet fact may be treated as current without checking its age against
> the mutation clock.**

An unstamped topology map or credential table is a map of a world that may no
longer exist. Expiry is per fact CLASS, and derived rather than chosen
(`shared/strategy/dnet/knowledge.ts`):

| Class | Examples | Invalidated by |
|---|---|---|
| `identity` | `modelId`, `passwordFormat`, `passwordLength`, `difficulty` | **never by age** — only by the host disappearing, since a host that returns is cleaned and given a new password |
| `position` | `depth` | a move |
| `topology` | `neighbours` | a move, a disconnect, *or* a new connection — three compounding rates, so edges are the shortest-lived thing we hold |
| `resource` | `blockedRam`, `maxRam`, `hasSession` | a restart |

**Unless the host is outside the clock altogether.** Every branch of
`mutateDarknet` picks its victim from `getAllMovableDarknetServers`
(`DarkNet/utils/darknetNetworkUtils.ts:69-78`), which skips any server that
`isStationary` or `hasStasisLink` — so move, delete, disconnect and restart all
miss it alike. (`isImmutable`, `NetworkMovement.ts:227`, is a second and narrower
guard: it covers stasis links but *not* `isStationary`, so the pool exclusion is
what does the work for both.)

Immunity is therefore a property of the HOST, not of a fact class: nothing about
such a server ages, and since it cannot be deleted it is never forgotten either.
Upstream marks `darkweb` and the labyrinth stationary; showing darkweb's depth
expiring in a minute was the bug that made this worth writing down.

Rates add, times do not: a fact invalidated by any of several events dies sooner
than the fastest of them alone. The one number not derived is `TRUST_FRACTION`,
the fraction of the expected time at which we stop believing a fact; it is a
judgement call and is named rather than buried. This repository already names
that bug class for prestige — *"a topic that survives the reset is live data
from a dead node"* (`spec/features.md`) — and the darknet has the same hazard,
just far more often.

In practice:

- Knowledge lives as `HostFact<T> = { value, at }`, not as a bare value, and a
  `ReportHost` is stamped by the job that *looked* rather than by the drain that
  collected it. Facts merge last-writer-wins on that observation time, never on
  arrival order — a drain is a batch, and two residents adjacent to the same host
  will both describe it.
- A fact older than its expiry is *shown* but excluded from decisions, and the
  decision says which fact it is waiting on.
- A host unseen for long enough is **forgotten**, not remembered. Darknet hosts
  go offline permanently; keeping one forever is fabricating a map.
- **There is one host representation.** Home's own one-hop probe reports in the
  same `ReportHost` shape an agent does and folds into the same knowledge; the
  panel reads that fold and nothing else.
- There is no per-fact record of *which* agent saw it — that was carried once,
  read by nothing, and deleted. The generation is likewise checked once, on the
  whole rendezvous (`overseerIsLive`), because agents outlive controllers and
  what has to be refused is the channel rather than the record.

`tests/dnet-staleness.test.ts` pins these as behaviour.

## The shape that follows: an overseer, residents, and a spawn chain

Two processes share the word "controller", so this document names them: the
**home driver** is `start.js`'s dnet feature driver, pinned inside home's 3.6 GB
static budget (`tests/ram-budget.test.ts`); the **overseer**
(`game/dnet/overseer.ts`) is the darknet's own controller, 1.65 GB, living on
`darkweb`.

**Home cannot play the feature.** `probe()` is host-local, so from `home` the
darknet is one host wide; a session belongs to the PID that won it, so a dodge
stub cannot win one on anyone's behalf; and putting `ns.dnet.*` or `ns.scp`
into `start.js`'s billable surface would break the 3.6 GB pin that is the whole
reason the dodger exists. So the home driver only seeds the beachhead (`scp` +
`exec` onto `darkweb`, pinned to home — see the check order above), drains what
the overseer has learned, and sends orders home alone can compute (charisma,
netDepth, bitNode, the vault replay).

**Something long-lived has to live out there** and hold the accumulated map:
the overseer. It must not die, which means it can never `spawn` — `spawn` kills
its caller — and it should not `exec` either, because `exec` leaves the caller
alive and two allocations at once is usually RAM a darknet host does not have.
So it launches nothing: it keeps a QUEUE per host, and each host keeps exactly
one **resident** — the only thing that can start work there. When the resident
takes a job it `spawn`s into it with `spawnDelay: 0`, which kills the resident
and starts the job on the same host; the job runs and spawns back. A host holds
one agent process at a time, and its peak RAM is the largest single job rather
than the sum of the work.

`spawn` costs 2.0 GB against `exec`'s 1.3, and every job pays that tax on the
way back. It is still the cheap option, because the alternative is holding two
allocations at once — and because a host left with no resident cannot be
repaired from outside: planting one needs a session AND adjacency.

**The rule that nearly makes this impossible.** A session belongs to the PID,
and `spawn` ends the PID, so a job that authenticates cannot hand its session to
the next process. `connectToSession(host, password)` re-opens one at any
distance, with no delay and no connection requirement, for **0.05 GB**. That
single cheap call is what makes the whole chain affordable. Its one
precondition: it passes `requireAdminRights`, which only a successful
`authenticate` ever sets — so it re-opens a session on a host we have opened
once, and cannot open a NEW one. Log-leaked passwords belong to hosts we may
never have touched, so the first use of one has to be the 0.4 GB call;
`plantJob` tries the cheap path and falls back.

The overseer costs 1.65 GB static — the base plus `getHostname` — and describes
jobs it cannot afford to run as closures calling through bracket notation on an
ns it does not own, so the analyser charges the agent's declared `ramOverride`
instead. Same trick as `game/lib/dodge.ts`; `tests/ram-budget.test.ts` checks
the declared method lists against the calls the closures actually make, because
the simulator does not model the dynamic-RAM check and an under-declared job
passes every sim run and dies in the game.

**Agents outlive both controllers.** `reclaimFleet` (`game/lib/net.ts`) walks
only servers from the ordinary `ns.scan` snapshot, and darknet hosts are never
in it — so a dnet agent survives an overseer death, a cold boot, a build handoff
and a page reload. That is precisely the durability BN15's flavour text asks
for, and its cost is the generation stamp: a stale agent can keep reporting from
a run that no longer exists, which is why the generation is checked at every
rendezvous.

### Transport: the realm

**One convention, as engineering rather than fair play: the page realm carries
the conversation, and every entry in it is expired rather than trusted.**

An earlier version pushed observations, credentials and orders over three
netscript ports; the realm replaced them. That is not a shortcut past a game
rule — ports are themselves documented as shared across all hosts, 0 GB, no
session, so the realm is a faster version of a sanctioned mechanic, and what
preserves the challenge is enforced by the engine: per-PID sessions, host-local
`probe()`, target-only `setStasisLink`/`phishingAttack`, and the network killing
your scripts. The realm also does what a port cannot: the overseer hands each
resident a **live function reference** — a closure over calls it cannot afford
itself — which is the mechanism behind the 1.65 GB figure above.

The hazard is real — a realm map holds live references that outlive the servers
they describe — so the realm is allowed only under four rules, each enforced in
code (`game/dnet/realm.ts`):

1. **Entries are expired by the overseer, never trusted.** A resident that stops
   beating is swept and its queue retired (an active job counts as life until
   its own timeout); a job that stops settling is timed out and its promise
   rejected. A promise that never settles is a process that was killed, and out
   there that is the common case.
2. **The rendezvous holds work, never knowledge.** `drain()` hands each
   observation to home ONCE, and home folds it into knowledge it owns — so an
   overseer dying loses scheduling, not the map.
3. **A foreign generation is refused**, by the overseer's election and by every
   agent on every pass. Agents outlive controllers, so a live script from a dead
   run really can be talking to us.
4. **A credential lives only in the realm and in home's vault.** It is never
   published to a topic and never written to a log; what the panel gets is a
   boolean. `stripCredentials` enforces that recursively at the one place
   anything is recorded.

`tests/dnet-staleness.test.ts` pins the fourth, and
`sim/tests/dnet-session.test.ts` pins the engine rules the first three
compensate for.

### Observability

Agents emit their own telemetry over their own `new WebSocket()` — a browser
global, 0 GB. It is **send-only**, so it cannot become a back-channel, and a
`--perf` build removes it entirely, which is the mechanical proof that no
decision depends on it. Agents pass their install identity in `ns.args` rather
than reading the realm, so `ui/store.ts` groups them into the controller's run
artifact.

The metric worth keeping: agent telemetry leaves the game the instant an agent
sees something, while home's `known` state only advances when a report is
drained. A host that appears as `observed` and never becomes `known` is an agent
that died before reporting — the gap is a direct read on **agent mortality**,
which, since the transport does not lose data, is the loss that actually matters
out there.
