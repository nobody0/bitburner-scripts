# BN13 — They're lunatics

> *"1 step back, 2 steps forward"* · theme: `stanek`

**In-node:** the **Church of the Machine God** in Chongqing and **Stanek's
Gift** — a grid you place fragments on, charged by running scripts against them,
granting multipliers that scale with charge.

The entry cost is a sequencing rule, not a resource cost
(`Prestige.ts:184`): outside BN13, the Church is **banned** if you own any
augmentation other than NeuroFlux Governor. **Inside BN13 there is no ban** —
the check is guarded by `bitNodeN !== 13`. So in-node you may accept the Gift
whenever; elsewhere it must be a fresh install.

## Reading

- `HackingLevelMultiplier` 0.25 × `HackExpGain` 0.1 is the hardest hacking
  environment in the game, and every alternative is nerfed too (corp 0.001, gang
  0.3, bladeburner 0.45). The Gift at 2× is the only thing pointing up.
- "1 step back, 2 steps forward" is literal: give up the early augmentations to
  accept the Gift, then the Gift exceeds what you gave up.

## SF13

Church of the Machine God appears in other BitNodes; each level increases the
Gift's size.

**Ordering rule, stated in SF13's own text:** with **SF7 level 3**, joining
Bladeburner immediately grants The Blade's Simulacrum — an augmentation — which
would trip the Church ban. So with SF7.3 you must **accept Stanek's Gift before
joining the Bladeburner division**. See [`bn07.md`](bn07.md).

## The charge formula, and what it implies

`CotMG/formulas/effect.ts`:

```
effect = 1 + (ln(highestCharge + 1) / 60)
           * ((numCharge + 1) / 5) ^ 0.07
           * power * boost * StaneksGiftPowerMultiplier
```

`StaneksGift.charge(fragment, threads)` updates the two inputs:

```
threads > highestCharge :  numCharge = highestCharge * numCharge / threads + 1
                           highestCharge = threads
otherwise               :  numCharge += threads / highestCharge
```

Read the exponents and the strategy falls out: **`highestCharge` is the largest
single charge call's thread count and enters logarithmically, while `numCharge`
enters at the power 0.07 — almost flat.** So a few enormous-thread charges beat
many small ones by a wide margin, and grinding charge count is nearly worthless.
That is the opposite of the intuitive "keep it charged" loop, and it is a
concrete scheduling rule: save RAM for one big call rather than spending it
continuously.

`boost` comes from adjacent **Booster** fragments, so placement adjacency is
part of the same optimization, not a separate one.

Charging also pays Church reputation:
`faction_rep * threads^0.95 * (favor + 100) / 1000`.

## For our code

- `stanek` needs **fragment placement optimization** — 2-D packing with shapes,
  booster adjacency and per-fragment `power` — plus a charge scheduler built
  around maximising peak threads, not charge frequency.
- `progression` must treat accepting the Gift as a **one-shot, install-timed,
  irreversible** action, and must respect the SF7.3 ordering constraint. Nothing
  in our model expresses either today.
