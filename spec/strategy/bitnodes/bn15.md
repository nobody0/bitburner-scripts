# BN15 — The Secrets of the Dark Net

> *"The rules have changed"* · theme: `dnet`

**In-node:** the darknet — a constantly shifting network where servers move or
disappear, long-distance communication is unreliable, and scripts must be
"self-sufficient and durable, and spread themselves to stay alive". Access comes
from weak passwords and leaky logs.

**The headline rule:** *"In this BitNode, the Daedalus faction has not yet found
and monopolized the fabled Red Pill augmentation."* The Red Pill is out in the
dark instead — see the labyrinth, below.

**What the node is for.** Its own description states the objective plainly:
*"If you can take advantage of the darknet servers' weak passwords and leaky
logs, you will be able to gain access to the deepest parts of the darknet and its
secrets."* Destroying it grants SF15, or upgrades an existing SF15 to a maximum
of level 3. So the node is a password-and-traversal problem: reach depth by
cracking servers, under a network that rearranges itself while you work.

## Reading

- **`CharismaLevelMultiplier: 1.1` is the only stat buff in any BitNode.** The
  charisma that matters most is the **labyrinth ladder** —
  `LABYRINTH_CHARISMA = [300, 600, 1500, 2500, 3000, 3500, 4000]`
  (`shared/strategy/progression/endgame.ts`), seven gates for six rewards plus
  The Red Pill. SF15's own levels also scale off charisma. So `career` → `dnet`
  for charisma is a real edge — but see the cycle: `dnet` partly pays its own
  charisma bill through `phishingAttack()` and the labyrinth augmentations.
- `ScriptHackMoney` is untouched and `ServerMaxMoney` only 0.8 — **BN15 does not
  force you off the farm.** It is one of the mildest nodes for ordinary hacking.
- `DaedalusAugsRequirement: 20` is the lowest in the game.

## The labyrinth — a second Red Pill

`DarkNet/effects/labyrinth.ts` awards a fixed augmentation sequence. The
authoritative order is the **prereq chain** in `AugmentationTable`:

The W1ngs of Icarus → The B00ts of Perseus → The H4mmer of Daedalus →
The St4ff of Asclepius → The L4w of Bayes → The B1ade of Solomonoff

Then:

- **In BN15**, The Red Pill replaces **The L4w of Bayes** in that sequence, so
  four rewards precede it rather than six.
- **In any other node where `DarknetLabyrinthRewardsTheRedPill ≠ 0`**, The Red
  Pill comes after all six.
- The multiplier **defaults to 1**, and only **BN8** sets it to 0.

So the labyrinth is a Red Pill route in **thirteen of fifteen BitNodes**, not a
BN15 curiosity — and since SF15.1 unlocks the full dark web everywhere, it is a
genuine alternative to Daedalus's 2 500 000 rep. That has direct consequences
for [`bn01.md`](bn01.md).

The rewards are also an engine, not just a gate toll. Each costs `rep: 10000`
and `$1e6` with no faction, is `special: true`, and carries multipliers: five of
the six raise `charisma` (The St4ff raises `charisma_exp` instead), and five
carry **`dnet_money`** — 1.3 / – / 1.1 / 1.1 / 1.15 / 1.1 in the order above,
The B00ts being the exception. `dnet_money` is a real `Player.mults` field
covering "money gained from phishing and caches on darknet servers".

## The `ns.dnet` surface

Four facts shape every design here, and the API is built around them:

1. **There is no global view.** `probe()` returns only the darknet servers
   directly connected to *the calling script's own host* — from `home` that is
   just `darkweb`. `ns.scan` does not enumerate the darknet at all.
2. **Sessions are per-PID.** `authenticate` grants a session to the calling
   script instance only; any other script must call `connectToSession` itself. A
   session cannot be handed over by any means.
3. **Transfer is distance-free; execution is not.** `scp` *to* a darknet host
   needs a session but no direct connection, and `scp` *from* one needs nothing
   at all. `exec` needs a session **and** a direct connection, backdoor, or
   stasis link. So the hard problem is placing a running process, not moving
   data.
4. **The map moves.** `nextMutation()` resolves when servers move, restart
   (killing their scripts), go offline — often permanently — or appear fresh
   with new passwords.

| Call | Role |
|---|---|
| `probe()`, `getServerDetails`, `getDepth`, `isDarknetServer`, `getServerRequiredCharismaLevel` | Enumerate and select targets, all **local to the calling host** |
| `authenticate(host, password)` / `connectToSession(host, password)` | Access — the first needs a direct connection, the second does not. Both grant a session to the calling PID only |
| `heartbleed(host, options)` | Scrape logs. Needs a direct connection and **charisma ≥ the host's requirement**, but no session. Threaded, priced by `formulas.dnet.getHeartbleedTime` |
| `openCache(filename)` | Retrieve captured data. Returns `karmaLoss` — it is a karma sink, which couples it to `career` and `gang` |
| `memoryReallocation()`, `getBlockedRam()` | Free RAM held by the server owner's processes. Needs an authenticated, directly-connected target; scales with charisma and threads |
| `setStasisLink()`, `getStasisLinkLimit()`, `getStasisLinkedServers()` | **Takes no host** — pins the *calling script's own server* against moving or going offline. So pinning anything requires already running there. The global limit makes links scarce |
| `induceServerMigration(host)` | *Raises the chance* a connected, non-stationary host moves. Scales with threads and charisma. Cannot target its own host |
| `getDarknetInstability()` | Backdoor-induced **authentication** unreliability: `authenticationDurationMultiplier` and `authenticationTimeoutChance`. Unrelated to the map clock |
| `nextMutation()` | The map's own clock (0 GB) |
| `unleashStormSeed()` | Runs `STORM_SEED.exe` if present on the calling host. Documented as catastrophic |
| `promoteStock(sym)` | Raises a symbol's **volatility**, not its forecast. Earns nothing directly — it is a `stock` input |
| `phishingAttack()` | **Only from scripts on darknet servers.** Builds charisma, lifts money scaling with threads, occasionally yields a `.cache` file |
| `labreport()`, `labradar()` | Labyrinth. 0 GB, `Result<any>`, and documented only as riddles — whether they are getters or actions is **unknown** |

### The password mechanic

This is the feature's actual core challenge, and it is discoverable rather than
documented. `getServerDetails` returns, per host:

`modelId` — *"Similar models have similar vulnerabilities. The model list is
intentionally undocumented. You are supposed to experiment and discover the
models."* The full list is transcribed under **The server models** below, since
it is the taxonomy our strategy has to cover. Plus `passwordHint`, `data`
("Data from the passwordHint, if any"),
`passwordLength`, `passwordFormat` (`numeric | alphabetic | alphanumeric |
ASCII | unicode`), `logTrafficInterval`, `difficulty`, `isStationary`.

Two leaks tell us the shape of the puzzle:

- `formulas.dnet.getAuthenticateTime(details, threads?, player?,
  correctCharactersInPassword?)` documents its fourth parameter as **"only used
  for `2G_cellular` model servers"**. So at least one model leaks a
  per-character oracle through timing, and one model id is named.
- The in-game literature is the taxonomy. `Literature/Enums.ts` names eleven
  darknet `.lit` files whose enum keys say what each teaches:
  `FactoryDefaultHint = "factory-default.lit"`,
  `DogNameHint = "dog-name-ideas.lit"`,
  `PasswordServerHint = "partial-password-jutsu.lit"`,
  `TimingServerHint = "timing-attack.lit"`,
  `BinaryServerHint = "raw-data.lit"`,
  `StasisLinkHint = "stasis-link.lit"`,
  `ServerOfflineHint = "server-offline-problem.lit"`,
  `DarkWebRebootHint = "darkweb-rebooted-again.lit"`,
  `CacheHint1/2 = "cache-note-1/2.lit"`,
  `LabHint = "secrets-in-the-depths.lit"`, and `DarknetHandbook`.

That reads as at least five password classes — a known factory default, a
dictionary guess seeded by `passwordHint`, a partial-password prefix oracle, a
timing oracle, and raw binary — which is the roadmap for a cracking
implementation, sourced rather than invented.

`heartbleed` is the feedback channel: the `authenticate` docs say *"If
unsuccessful, more detail may be able to be gathered by using `heartbleed()` to
look at the resulting logs."*

## SF15

| Level | Effect |
|---|---|
| 1 | Permanently start with the **TOR router and DarkScape**, and unlock the full dark web in all BitNodes |
| 2 | Charisma raises **job salary and rep gain**; +20% authentication speed *(the code gates this on level > 2 — see Verified formulas)* |
| 3 | Charisma raises **faction work rep gain**; +50% xp and money from `.cache` files |

SF15.1 is the structurally interesting one: TOR permanently removes the
$200 000 early-game gate on port openers in *every* node, and full dark web
access is what makes the labyrinth route portable.

SF15.3's reputation effect is precise and transcribable
(`PersonObjects/formulas/Reputation.ts`): at level 3 and above, charisma is
added to the faction-work rate at **0.1×** for hacking work and **0.3×** for
security and field work. In field work that bonus is scaled by the share bonus
and charisma already counts at 1× separately; in security work it is not scaled.

Note that our capability gate is broader than SF15: darknet access is BN15, an
active SF15, **or** `DarkscapeNavigator.exe` on home
(`shared/features/unlock.ts`). The `.exe` path is not source-file gated.

## For our code

- `dnet` needs a `needs`-board edge to `career` for **charisma**, driven by the
  labyrinth ladder rather than by `getServerRequiredCharismaLevel`. It is not a
  one-way edge: `phishingAttack()` builds charisma, so `dnet` feeds back.
- **The first hop needs no credential.** `darkweb` is rooted, stationary,
  password-free, 16 GB with nothing blocked, and always authenticated, so `scp`
  and `exec` onto it just work. Password discovery is only needed past it.
- Darknet RAM is a **separate pool**, not fleet RAM. Darknet hosts never appear
  in `ns.scan`, so they are never in the server snapshot or the heap; part of
  their RAM is owner-blocked, and they can vanish. `memoryReallocation` grows
  that pool, not ours.
- `progression` should know the labyrinth exists as an alternative Red Pill
  route once SF15 is held.
- The remote-execution model, and the rules that follow from it, are in
  [`spec/dnet.md`](../../dnet.md).

## Verified formulas

The pinned checkout is restored at `../bitburner-src`
(`3162fd2590e221eadd0c0fbd46151913f7c4c41c`), so these are transcriptions, not
guesses.

**Authentication time** (`DarkNet/effects/effects.ts:60-89`):

```
baseTime      = 850
skillFactor   = (5 * requiredCharismaSkill + (difficulty + 1) * 100) / (charisma + 150)
threadsFactor = 1 / (1 + 0.2 * (threads - 1))          // diminishing returns
backdoorFactor    = 1.07 ^ max(0, backdoored - max(rootedMovable / (NET_WIDTH * 3), 2))
underleveledFactor = charisma <= requiredCharismaSkill && depth > 1
                     ? 1.5 + (requiredCharismaSkill + 50) / (charisma + 50) : 1
bootsFactor   = has The B00ts of Perseus ? 0.8 : 1
sf15Factor    = activeSourceFileLvl(15) > 2 ? 0.8 : 1
time = baseTime * skillFactor * backdoorFactor * underleveledFactor
       * bootsFactor * sf15Factor * threadsFactor
return time * intelligenceBonus(intelligence, 0.25)
       + (modelId === "2G_cellular" ? correctChars : 0) * 50 * threadsFactor
```

Three things worth reading twice:

- **The timing oracle runs the counter-intuitive way.** On `2G_cellular` each
  *correct* character makes authentication take **longer** (+50 ms × threads
  factor). Slower is closer, so the attack measures duration and climbs.
- **`underleveledFactor` only bites below depth 2.** At depth 0 or 1, low
  charisma costs nothing beyond `skillFactor`.
- **The SF15 auth discount is level 3, not level 2.** The code tests
  `activeSourceFileLvl(15) > 2`, while the API docs attribute "+20%
  authentication speed" to SF15.2. Code wins; the doc is wrong upstream.

**Heartbleed time** is `calculateAuthenticationTime(...) * 1.5`
(`NetscriptFunctions/Formulas.ts:492-498`).

**RAM freed per `memoryReallocation`** (`DarkNet/effects/ramblock.ts:71-83`):
`clamp(0.02 * 2 * 0.92^(difficulty+1) * threads * (1 + charisma/100), 0,
blockedRam)`, rounded to two decimals. Note how small that is — freeing
meaningful RAM is a many-call grind, scaled hard by charisma and difficulty.

**Instability is exactly the backdoor surplus.** `getBackdoorAuthTimeDebuff()`
is `1.07 ^ surplus`, where the free allowance is
`max(rootedMovableServers / (NET_WIDTH * 3), 2)` — so at least two backdoors are
always free, and the allowance grows as you root more of the net.

### Backdoors and stasis links

A backdoor is the only unlimited way to `exec` on a darknet host that is not
directly connected: `ns.exec` calls the darknet gate with
`backdoorBypasses: true` (`NetscriptFunctions.ts:641-646`), so
`backdoorInstalled` satisfies the direct-connection requirement. Without one, the
only other bypass is a stasis link — and there are at most four of those, ever.

Three costs attach to it:

1. **Global authentication slowdown** of `1.07 ^ surplus`, where the free
   allowance is `max(authenticatedMovableServers / 24, 2)` — so realistically
   only about two to four backdoors are free before every authentication on the
   net gets slower.
2. A ~9% chance per mutation tick that one backdoored host is restarted. A
   restart kills its scripts, clears `authenticatedPIDs`, and sets
   `backdoorInstalled = false` (`NetworkMovement.ts:301-311`).
3. A ~4% chance per tick that one backdoored host is deleted. Both branches
   `return` early, so they also skip the tick's remaining rolls.

`isImmutable(server) = openServer || isConnectedTo || hasStasisLink`
(`NetworkMovement.ts:227-228`) is checked by `deleteDarknetServer`,
`moveDarknetServer` and `restartServer`, each returning early on it. A
stasis-linked host is therefore not deleted, moved or restarted.

| | Count | Grants | Costs |
|---|---|---|---|
| Backdoor | unlimited | remote `exec` | auth slowdown past the free allowance; restart/delete targeting; the restart clears the backdoor |
| Stasis link | 1-4 | remote `exec`, and exemption from delete/move/restart | a limited slot; 12 GB and `(1000 / (charisma + 1000)) * 30_000` ms on the target |

`moveDarknetServer` deletes a server outright if `getAllOpenPositions` returns
nothing for it, so a full net loses hosts through the move path as well as the
delete path.

**The mutation clock, exactly.** `getDarknetCyclesPerMutation()` is
`(rateMultiplier * 150) / depth` cycles of 200 ms, `rateMultiplier` being 1 in
BN15 and **2 everywhere else**. At the default depth of 10 that is a tick every
**3 seconds** in BN15 and 6 elsewhere, and it accelerates as the labyrinth
deepens — partly offset past depth 16 by `mutateDarknet`'s own
`16 / depth` throttle roll. One tick then rolls independently for island moves
(30%), low-level restocking (30%), deleting 1-4 servers (10%), adding 1-4 (10%),
restarting one (20%), moving three (30%), adding connections (50%), and severing
every connection on one host (50%) — so most ticks change something, and a fair
number change nothing.

The consequence for our code is that the *net* churns in seconds while any *named
host* is stable for minutes, because a tick touches only a few of
`depth × NET_WIDTH × SERVER_DENSITY` servers. Both figures are transcribed in
`shared/strategy/dnet/rates.ts`, and the knowledge expiry is derived from them.

**Stasis links** (`DarkNet/effects/effects.ts:211-216`): the limit is
`1 + TheBrokenWings + TheHammer + TheStaff`, so **1 to 4**, raised only by those
three labyrinth augmentations. Applying one takes
`(1000 / (charisma + 1000)) * 30_000` ms. That closes a strategic loop the docs
never noted: labyrinth rewards buy stasis capacity, stasis capacity holds more of
the graph, and holding the graph is what makes the labyrinth walkable.

`darkweb` itself is generated by `initDarkwebServer()`
(`DarkNet/controllers/NetworkGenerator.ts:52-89`) and is a special case in every
way that matters to us:

```ts
modelId: ModelIds.NoPassword, password: "", staticPasswordHint: "There is no password",
depth: -1, difficulty: 0, preventBlockedRam: true
darkweb.isStationary = true; darkweb.hasAdminRights = true;
darkweb.blockedRam = 0;      darkweb.maxRam = 16;
```

So `darkweb` has **16 GB, none of it blocked, already rooted, never moves, and no
password** — and `isAuthenticated()` short-circuits `true` for it
(`DarkNet/effects/authentication.ts:199-205`), as does the `exec`/`scp` gate:
*"We always are authed to ourselves and DarkWeb. Early-out past the last checks."*
(`DarkNet/effects/offlineServerHandling.ts:98-101`). Its `depth` of `-1` also
confirms that depth 0 is its children, not itself.

**Consequence for our code: the first hop is free.** `scp` and `exec` onto
`darkweb` need no credential, no session and no cracking — only TOR, which
connects it to home. Everything past `darkweb` needs a password.

## Server population and size

The net is a grid: `NET_WIDTH = 8` columns by `getNetDepth()` rows, filled to
`SERVER_DENSITY = 0.6` (`LOW_LEVEL_SERVER_DENSITY = 0.7` for the shallow rows).
`populateDarknet` seeds `getNetDepth() * NET_WIDTH * SERVER_DENSITY - 10`
servers, then tops rows 0 and 1 up to five each, then calls
`balanceDarknetServers()`. Row `AIR_GAP_DEPTH = 8` holds none.

`getNetDepth()` is the current labyrinth's depth, so the net grows as the
labyrinth is walked (`DarkNet/effects/labyrinth.ts`, `labData`):

| Lab | Net depth | Charisma | Solved by |
|---|---|---|---|
| *(before full darknet access)* | 5 | 300 | — |
| NormalLab | 7 | 300 | **manual** |
| CruelLab | 12 | 600 | **manual** |
| MercilessLab | 19 | 1500 | script |
| UberLab | 23 | 2500 | script |
| EternalLab | 29 | 3000 | script |
| EndlessLab | 31 | 3500 | script |
| FinalLab | 36 | 4000 | script |
| BonusLab | 36 | 4000 | script |

So roughly 14 servers at depth 5, ~24 at depth 7, and ~163 at depth 36. Depth
also sets the mutation rate, so a deeper net is both larger and faster-moving.
`manual: true` on the first two labs means those two mazes are solved in the UI,
not by a script.

## RAM on darknet servers

`maxRam` is rolled at construction (`DarknetServerOptions.ts:206-211`):

```
baseRam = 16 * 2 ** floor(difficulty / 6)
maxRam  = max(baseRam * pick([0.5, 1, 1, 1.15, 1.4]), 16)
```

so 16 GB minimum, doubling every 6 difficulty steps — 128 GB and more in the
deep net. `blockedRam` is then rolled from `maxRam`
(`ramblock.ts:97-110`), and it is a large fraction of the total:

| `maxRam` | `blockedRam` drawn from |
|---|---|
| 16 | `[0, 1, 2]` — index over the first **2** entries only, so 0 or 1 |
| ≤ 32 | `[0, 2, 4]` — likewise 0 or 2 |
| ≤ 64 | `[16, 32, maxRam - 8]` |
| > 64 | `[maxRam, maxRam - 8, maxRam - 64, maxRam / 2]` |

A large server can therefore arrive with **all** of its RAM blocked.
`server.updateRamUsed(server.blockedRam)` is applied at construction, by
`applyRamBlocks()`, and again in `NetscriptWorker.ts:243` whenever a server's
used RAM is recalculated — so blocked RAM presents as *used* RAM and cannot be
allocated. Usable RAM is `maxRam - blockedRam`.

`memoryReallocation` reduces `blockedRam` by
`clamp(0.02 * 2 * 0.92^(difficulty+1) * threads * (1 + charisma/100), 0,
blockedRam)`, awards `charisma_exp * threads * 10 * 1.1^difficulty` charisma xp,
and when `blockedRam` reaches 0 on a non-labyrinth server calls
`addCacheToServer(server, false)` — clearing a server's block yields a `.cache`
file.

### What that RAM can and cannot run

- **`hack`, `grow` and `weaken` cannot target a darknet server.** They resolve
  through `getNormalServer`, which rejects anything that is not a `Server` with
  "The server must not be a darknet server."  `DarknetServer extends BaseServer`,
  not `Server`, so it has no `moneyAvailable`, `hackDifficulty` or
  `requiredHackingSkill` at all. (`Hacking.ts:60-61` returns a flat 16 seconds
  for a darknet server, which is reachable only through the terminal `hack`
  command, not through ns.)
- **Scripts running *on* a darknet server are ordinary scripts.** `cpuCores` is
  fixed at 1, and the class comment states cores are "included to make sure that
  grow etc on the server work as expected" — i.e. as the execution host for work
  aimed at ordinary servers.
- Its RAM is not fleet RAM: `ns.scan` omits darknet servers, so they never enter
  the server snapshot or the heap.
- A restart kills every script on the host and clears its sessions; a delete
  takes its files too.

## Passwords

Every non-labyrinth server has a `password`, a `modelId` naming its minigame, a
`staticPasswordHint`, and `passwordHintData`. `MAX_PASSWORD_LENGTH` is 50.
`getServerDetails` exposes `passwordLength` and `passwordFormat`
(`numeric | alphabetic | alphanumeric | ASCII | unicode`), the hint and its data,
but never the password.

**The oracle is `heartbleed`'s log ring, not the return value of `authenticate`.**
This is the opposite of what it looks like, and getting it backwards makes the
whole password mechanic seem unreachable from a script.

`handleAuthentication` builds a model-specific `PasswordResponse`
(`{code, message, data, passwordAttempted}`) on a wrong password — but
`authenticate()` only forwards its `data` for the **labyrinth**:

```ts
// NetscriptFunctions/Darknet.ts:163-177
if (isLabyrinthServer(server.hostname)) {
  return { success, code, message: authResult.response.message, data: authResult.response.data };
}
return { success, code, message: success ? Success : AuthFailure };   // no data, generic message
```

For every other model the response is written to the server's own log ring by
`logPasswordAttempt` (`DarkNet/effects/authentication.ts:174-177` →
`DarkNet/models/packetSniffing.ts:90-125`), and comes back only through
`heartbleed`, which serialises each entry as
`typeof log.message === "string" ? log.message : JSON.stringify(log.message)`
(`NetscriptFunctions/Darknet.ts:286-288`).

So the oracle loop is **`authenticate(wrong)` → `heartbleed(peek)` → parse the
JSON lines**, and both halves must be the same agent standing on the same host —
`heartbleed` needs a direct connection too. That is a hard constraint on where
the cracking code can live, not an implementation detail.

### The logs leak passwords outright

`heartbleed` is not only the oracle channel; it is a **credential channel**, and
this is the "leaky logs" the node description names. `getLogNoise`
(`DarkNet/models/packetSniffing.ts:154-192`) emits one line per
`logTrafficInterval`, drawn from:

| Line shape | What it leaks | Chance |
|---|---|---|
| `Connecting to <host>:<password> ...` | a **neighbour's plaintext password** | `0.05 x 1/(difficulty+1)` |
| `Logging in with passcode: <password> ...` | **this host's own password** (`OpenWebAccessPoint` only) | ~0.3 of its noise draw |
| `--<password>--` | a random *movable* host's password, unattributed | 0.05 |
| `There's definitely a X and a Y...` (8 templates) | two characters contained in this host's password | 0.1 |
| `The characters A, B are in the right place.` | which characters of the **last attempt** were correctly placed | 0.1 |
| `[sending transaction details to <host>.]` | a topology edge | 0.05 |
| `<time>: <host> - heartbeat check (alive)` | liveness | otherwise |

`capturePackets` additionally embeds ` <hostname>:<password> ` inside a ~130-char
junk blob whenever `difficulty <= 16`, and the bare password above that.

The consequence for strategy is large: **a log-mining pass is a credential source
independent of every one of the 24 minigames.** Combined with the difficulty
tiering below, it is why the shallow net can be traversed without solving a
single password puzzle.

`requiredCharismaSkill` is rolled as
`max(floor(depthScaling + levelVariance), 1)` where
`depthScaling = depth < 2 ? depth * 10 : (depth / labDepth) ** 1.5 * labCha *
0.85` and `levelVariance = (random * 3 - 1) * depth`. `logTrafficInterval` is
`1 + 30 * 0.9 ** difficulty` seconds.

## Cache files

`.cache` files sit on a server in `DarknetServer.caches` and are listed by
`ns.ls`. They are created by clearing a server's blocked RAM, and by
`phishingAttack()` — a phishing cache is named `.d.cache`.

`openCache(filename)` deducts `difficulty + 1` karma (returned as a negative
`karmaLoss`) and yields one reward drawn at random from:

- a program or stock-market-related reward,
- a stock reward,
- a data file (`DarknetConstants.DataFileSuffix` is `.data.txt`),
- a coding contract — **only** for `.d.cache` files, i.e. from phishing,
- money — **only** when the node's `DarknetMoneyMultiplier` is non-zero.

On a labyrinth server, the labyrinth cache instead calls `getLabReward()`.

The program/market branch is the valuable one, and it is an ordered ladder
(`cacheFiles.ts:130-168`): the first program not already owned, walking
`ServerProfiler, BruteSSH, DeepscanV1, FTPCrack, AutoLink, relaySMTP,
DeepscanV2, HTTPWorm, SQLInject, Formulas` — so a cache can hand over
**`Formulas.exe`**, which the dark web sells for $5b. Once all ten are held it
grants, in order, a **WSE account** ($200m) and then **TIX API access** ($5b).

Then it grants `has4SData` — and that is the **$1b ticker, not the $25b script
API**. `shared/strategy/stock/decide.ts` documents that `getForecast` and
`getVolatility` check `has4SDataTixApi`, which caches never grant, so the free
4S is worth an automated player exactly what the purchase we deliberately never
make is worth: nothing. When everything above is held the branch falls through
to money.

The money reward is
`1.2^difficulty × 1e7 × (200 + charisma)/200 × sf15_3 × crime_money ×
dnet_money × DarknetMoneyMultiplier`, where `sf15_3` is 1.5 at SF15.3. That is
the only place `dnet_money` is read, which is what makes the five labyrinth
augmentations carrying it pay for themselves.

Upstream attributes this to a `darknet` money source (`MoneySourceTracker`),
which the ns `MoneySource` interface does **not** expose — so a script cannot
see darknet income as its own line.

## The labyrinth augmentations

Six, chained by `prereqs`, plus The Red Pill. They are not bought:
`getLabReward()` calls `Player.queueAugmentation(reward)` directly, so they cost
no money and no reputation and belong to no faction — `factions: []` and
`special: true` in the augmentation table. Being queued, they still require an
install to take effect. If the next reward is already owned, the cache awards
**NeuroFlux Governor** instead.

Three of them raise the stasis-link limit by 1 each: The W1ngs of Icarus, The
H4mmer of Daedalus and The St4ff of Asclepius (`getStasisLinkLimit`). The B00ts
of Perseus multiplies authentication time by 0.8.
